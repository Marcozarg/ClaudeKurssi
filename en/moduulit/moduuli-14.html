Core ~30 minOptional ~15 minPro / Max

Claude without a user: claude -p

So far you have had a conversation with Claude. In automation there is nobody to answer questions: a script, a schedule or a CI job gives Claude a task and reads the result. This is a headless run, and you make one by adding the option -p (print) to the claude command:

claude -p "What does the auth module do?"
cat build-error.txt | claude -p "Concisely explain the root cause of this error"
  • Claude does the task, prints the answer and exits. On success the exit code is 0, on failure it is not 0, so a script can branch on it.
  • Piped input (stdin) is read as well. The limit is 10 MB.
  • When a permission question would come up, nobody is there to answer. Unless something approves it separately, a call that would need approval is denied. That is why permissions and tools are decided in advance (the section "Running safely").
  • --output-format json returns the answer as JSON: the text is in the field result and the estimated cost in total_cost_usd. The other formats are text (default) and stream-json.
A headless run is the same Claude Code as everywhere else, not a lighter version. It can read, edit and run commands with exactly the rights you give it.

A script that calls Claude

This Bash script sends a branch's changes to Claude and prints the typos it finds. It belongs in a CI job, in a GitHub Actions runner or in Git Bash. Save it as typo-check.sh:

#!/usr/bin/env bash
set -euo pipefail

base="${1:-main}"
result=$(git diff "$base"...HEAD | claude -p \
  "Find typos in this diff. Return one line per typo: file:line and the typo. Nothing else." \
  --output-format json \
  --max-turns 3 \
  --max-budget-usd 0.50)

echo "$result" | jq -r '.result'
echo "estimated cost: $(echo "$result" | jq -r '.total_cost_usd') USD" >&2
  • set -euo pipefail stops the script when any step fails. A failure is not counted as success.
  • The diff arrives through a pipe, so Claude does not need permission to run git commands.
  • --max-turns limits the number of steps and --max-budget-usd the estimated cost in dollars. Both work only in a -p run. The cost is Claude's own estimate and can differ from the bill, so leave some headroom below your limit.
  • jq picks the result out of the JSON answer.

On Windows in PowerShell the same thing works like this (the quoting follows PowerShell's rules):

(git diff | claude -p "Find typos in this diff. Return one line per typo: file:line and the typo. Nothing else." --output-format json --max-turns 3 | ConvertFrom-Json).result

Running safely: permissions, limits and costs

An unattended run is more dangerous than a conversation, because nobody notices a mistake in time. Three rules:

  • Give only the tools that are needed. --allowedTools "Read" allows reading only. Commands are narrowed with patterns: Bash(git diff *) allows only commands that start with git diff. The space before the star matters.
  • Pick the permission mode for the task. --permission-mode acceptEdits approves file edits. --permission-mode dontAsk denies everything that is not explicitly allowed and suits locked-down CI runs. Do not use bypassPermissions or --dangerously-skip-permissions in a run nobody watches (modules 7 and 12).
  • Set ceilings. --max-turns, --max-budget-usd and the CI job's time limit (timeout-minutes on GitHub, timeout on GitLab) stop a faulty loop from running on.
Way to runWho pays
claude -p on your own computer, signed in with your subscriptionYour subscription's usage limit.
claude --bare -p or a CI job with ANTHROPIC_API_KEYThe API bill, per token (module 15). --bare does not use the subscription sign-in.
A GitHub Action with claude_code_oauth_tokenYour subscription's usage. Created with claude setup-token and tied to one person's subscription.
For shared work, use the organization's API key, not one person's subscription. The key is stored as a CI secret, never in code, in a log or in a chat (module 0). Ask the organization about the key and the billing before you create any.

Inputs are untrusted data in CI as well: the text of a pull request, an issue or a file can contain instructions for Claude. Keep the tools of an unattended job so narrow that a successful injection has nowhere to go (module 12).

Mods in a headless run

According to Anthropic's guide, claude -p discovers and loads installed plugins, hooks, MCP servers and CLAUDE.md files the same way an interactive session does, unless you use the option --bare. A mod is a plugin, so a mod installed on the machine also loads in a claude -p call run without --bare. A headless run has no user interface, so the status line, the toast and the band are shown to nobody, and there is nobody to answer a permission question.

  • --bare skips installed plugins. Then the mod does not load and its check is not done at all. The hooks of a plugin given with --plugin-dir do not run in bare mode either.
  • dontAsk does not rule mods out. According to the guide, a mod you installed can still approve some calls in this mode too.
  • The runner on GitHub or GitLab is a clean machine. It has only the mods that the job itself installs.
What reach-band does in a claude -p run has not been tested. We do not know what happens to a tier 3 call there: whether it asks, blocks or lets the call through. Do not rely on it in an unattended run. Use tight --allowedTools limits and a permission mode, --max-turns and --max-budget-usd limits, a time limit and a disposable runner instead. reach-band's tiers and the tested environments: module 13.

GitHub Actions

Anthropic's official action is anthropics/claude-code-action. When a workflow gives it a prompt input, it runs in automation mode: Claude runs on an event (a schedule, for example) without an @claude mention, and the result appears in the workflow run log. Without a prompt input it answers @claude mentions in issues and pull requests.

Preparation: install the Claude GitHub App on the repository (or run /install-github-app in Claude Code) and store the API key as a repository secret named ANTHROPIC_API_KEY. You need admin access to the repository.

The file .github/workflows/daily-report.yml summarizes yesterday's commits and the open issues every day at 09:00 UTC:

name: Daily Report
on:
  schedule:
    - cron: "0 9 * * *"
  workflow_dispatch:
jobs:
  report:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    permissions:
      contents: read
      issues: read
      id-token: write
    steps:
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: "Generate a summary of yesterday's commits and open issues"
          claude_args: |
            --max-turns 5
            --allowedTools "mcp__github__list_commits,mcp__github__list_issues"
  • ${{ secrets.ANTHROPIC_API_KEY }} is a reference to the secret. The value of the key is never written into the file.
  • claude_args passes Claude Code's options through. --allowedTools gives Claude just two GitHub tools; with a plain-text prompt and no such line Claude has neither a shell nor GitHub access.
  • timeout-minutes is the job's time limit. workflow_dispatch lets you start the job by hand for testing.
  • GitHub runs scheduled workflows only from the default branch, and in a public repository the schedule is switched off after 60 days without repository activity.
  • The action rejects runs started by a bot unless the bot is listed in the allowed_bots input.

GitLab CI

The GitLab CI/CD integration is still in beta in Anthropic's guide, and GitLab maintains it. It has no action of its own: you install Claude Code into the runner and call the same claude -p command. The API key is stored on the page Settings → CI/CD → Variables as a masked variable named ANTHROPIC_API_KEY.

This job goes through a merge request's changes with read-only access. The file .gitlab-ci.yml:

stages:
  - ai

mr-review:
  stage: ai
  image: node:24-alpine3.21
  timeout: 15m
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  before_script:
    - apk add --no-cache git curl bash
    - curl -fsSL https://claude.ai/install.sh | bash
    - export PATH="$HOME/.local/bin:$PATH"
  script:
    - git fetch origin "$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"
    - >
      git diff "origin/$CI_MERGE_REQUEST_TARGET_BRANCH_NAME"...HEAD |
      claude --bare -p "Review this diff. List bugs and risks briefly."
      --allowedTools "Read"
      --max-turns 5
      --max-budget-usd 1.00
  • The install lines follow Anthropic's guide: the installer puts the claude command in ~/.local/bin, which is not on the path in this image, so PATH is set.
  • claude reads the key from the environment variable ANTHROPIC_API_KEY. --bare needs it, because it does not use the subscription sign-in, and it keeps the job the same on every machine.
  • The ceilings are the same as in the script: --max-turns, --max-budget-usd and the job's timeout.
  • How the diff is built (fetching the branch and the comparison point) depends on your repository's settings. Try it on a small merge request first.

Guide: Claude Code GitLab CI/CD. A ready-made example of a job that answers mentions (@claude, GitLab MCP tools) and the Amazon Bedrock and Google Cloud options are there.

Scheduled tasks and /loop

If a task repeats, you do not need to run it yourself. Claude Code has three ways to schedule:

Cloud task (/schedule)Desktop task/loop
Where it runsOn Anthropic's cloudOn your computerOn your computer
Computer must be onNoYesYes, and the session must be open
Local filesNo, a fresh cloneYesYes
Shortest interval1 hour1 minute (1 hour in the forms)1 minute
  • A cloud task (called a "routine" earlier in Anthropic's guide) is a saved prompt, one or more repositories and connectors. It is available on the Pro, Max, Ultra, Team and Enterprise plans, and it is a research preview, so the feature may change. Create it with /schedule or at claude.ai/code/routines, for example /schedule daily PR review at 9am. Runs use your subscription's usage limit like ordinary sessions. In the cloud the session starts in auto mode, and the task works with the connectors it sees, as you, so remove the connectors it does not need.
  • /loop repeats a prompt inside a session, for example /loop 5m check if the deployment finished and tell me what happened. Without an interval Claude picks one itself. The repeat stops when the session is closed, and a recurring task expires after seven days. It suits short-term watching, not permanent automation.
  • Permanent scheduling in CI: a GitHub Actions schedule trigger (above) runs the job without your own computer.

Exercises

1. Run claude -p on a diff

Needs: a Pro subscription, Claude Code and a git repository with changes. No Pro or Claude Code? Copy the output of git diff into a claude.ai chat (Free) and ask for the same task: typos as file:line and the typo.

Make a small change with a deliberate typo in a disposable folder and run the PowerShell line from the section "A script that calls Claude". How much did the run cost? Change .result at the end of the line to .total_cost_usd and run it again.

Show example answer

The output is a line of the form file:line and the typo, for example README.md:3 "teh" should be "the". The JSON answer also has the fields session_id and total_cost_usd; the estimated cost of one small diff is typically a fraction of a cent. If the -p call prints nothing, check the exit code ($LASTEXITCODE) and that you are signed in. Missing authentication is printed as the result, not raised as an exception.

2. Run a scheduled job in CI

Needs: a repository on GitHub or GitLab, admin access, an API key with the organization's permission, and the Claude GitHub App on GitHub. No CI access or key? Read the GitHub and GitLab examples and answer on paper or in a claude.ai chat (Free): which tools does Claude have, what limits the cost and where does the key come from?

Copy the suitable example into your repository, store the key as a secret or a masked variable and start the job by hand (workflow_dispatch on GitHub, Run pipeline on GitLab). Confirm from the log that the job succeeded and that it used only the allowed tools.

Show example answer

On GitHub the result appears in the workflow run's log, not as a comment. If the run fails on authentication, check that the secret's name is exactly ANTHROPIC_API_KEY and that the job received it (on GitLab the variable may be protected to a branch other than the one you run on). Answer for the paper version: the GitHub job has two read-only GitHub tools (--allowedTools); the cost is limited by --max-turns 5 and timeout-minutes; the key comes from the secret secrets.ANTHROPIC_API_KEY. The GitLab job has only Read; the cost is limited by --max-turns, --max-budget-usd and timeout; the key comes from the masked CI/CD variable.

3. Review a dangerous job

Needs: nothing; reading and a list are enough, or claude.ai (Free) if you want a second opinion.

A colleague proposes this command for an overnight run that reads new issues, emails and web pages:

claude -p "Handle all new issues" --dangerously-skip-permissions

List what is missing or dangerous, and fix the command.

Show example answer

The faults: (1) all permissions are skipped, so Claude can run anything without asking; (2) no tool limit; (3) no --max-turns and no --max-budget-usd limit, so a mistake can burn money all night; (4) issues are untrusted input, and an injection would get to use every right (module 12); (5) no time limit and no disposable environment. Fixed: claude -p "Summarize the new issues" --allowedTools "Read" --permission-mode dontAsk --max-turns 5 --max-budget-usd 1.00 in a disposable runner with a time limit. The more the job may do (write, run commands), the tighter the limits must be.

Optional: structured output, sessions and checks

  • An answer that follows a schema: --output-format json together with --json-schema returns the result in the field structured_output. Check that the field exists before your script uses it: if Claude declined, it is not there.
  • Continue a conversation: claude -p "..." --continue continues the latest conversation and --resume a specific session by its session_id.
  • Rule out questions entirely: --permission-prompts none (Claude Code 2.1.259 or later) denies everything that would otherwise ask unless a hook or mod allows the call, and tells Claude nobody can approve the request.
  • Check that a plugin loaded: in a --output-format stream-json run, the system/init event lists the loaded plugins (plugins) and the load errors (plugin_errors). CI can fail if a plugin is missing.
  • A plugin in a GitHub Action: the inputs plugin_marketplaces and plugins install a plugin before the run. A ready example is in the GitHub Actions guide under "Run a skill".
  • No stored key: an organization can use the workflow's OIDC token (workload identity federation), so the repository holds no long-lived secret. The guide is on the GitHub Actions page under "Set up for an organization".
  • A ready-made review: if you do not want to maintain your own workflow, Anthropic's Code Review reviews pull requests automatically.
