Way of working

Core ~45 minOptional ~20 minPro / Max

Why the way of working decides

Claude does a lot quickly, including wrong things. A good result does not come from one perfect prompt but from repeated habits: a plan before code, a question instead of guessing, a test before a fix, a check before the work is declared done. In this module you adopt the core habits, install Matt Pocock's skills plugin and go through the whole flow from idea to implementation.

The module builds on earlier ones: plan mode and CLAUDE.md (module 7) and git (module 8) are the tools here.

Core habits

A checklist you can give Claude as its own instructions. Every rule has a reason, and the reasons are found in the coding-style.md base on this page.

  1. Plan first. For a non-trivial change, Claude first states the approach, the options and a recommendation. Code only after you say "proceed". Plan mode (Shift+Tab) makes this mandatory.
  2. Ask, do not guess. An unknown path, version or setting is looked up in the repository or asked from you. A confident guess looks exactly like a fact.
  3. Test first. Every new behaviour and every confirmed bug gets a test that fails without the change. The test is run first and seen red, then the change that turns it green is made.
  4. Check before "done". Claude runs the tests and says what was run and what was not. The words "works" and "verified" belong only to things that were run.
  5. Give a check that passes or fails. A test or another command Claude can run itself. Ask for the command it ran and its output as evidence; "all tests pass" on its own tells you very little.
  6. Hard rules go in hooks or deny rules. CLAUDE.md is guidance that Claude may decide does not apply. If something has to happen or be blocked every time, make it a hook or a permission deny rule.
  7. Short commits. One short line, one logical change. Commit and push are separate steps.
  8. No secrets. Passwords, keys and .env files do not belong in the conversation, in plans or in commits. Refer to the place where the secret is.

Source: code.claude.com/docs/en/best-practices, checked 11/2026.

Follow your organization's rules on what information may be given to an AI service. When in doubt, ask first.

Matt Pocock's skills plugin

Matt Pocock has published a collection of skills that implement the way of working above as ready-made commands: interview, spec, tickets, test-driven implementation and code review. Source and descriptions: github.com/mattpocock/skills. The content of the skills is his work, so this page only describes them and does not copy them.

Installation

The plugin's README gives Claude Code one command. Run it in a normal terminal:

claude plugin install mattpocock-skills@claude-plugins-official

You can run the same inside Claude Code with the command /plugin install mattpocock-skills@claude-plugins-official. Then the /plugin panel opens, where you choose the installation scope: Install for you (user scope) is enough for your own use. Claude Code adds the official claude-plugins-official catalog itself the first time you start an interactive session. Guide: code.claude.com/docs/en/discover-plugins.

Check the installation by typing /: the plugin's skills show up in the form /mattpocock-skills:name.

A plugin can contain instructions that Claude follows. Read the description in the installation view before you approve the installation.

Per-repo setup: once in every repo

Open claude in the repo's folder and run /setup-matt-pocock-skills. The skill asks where issues and tickets are kept (GitHub, GitLab or local markdown files), which status labels are used and where documentation is saved. The answers are saved in the repo, so the other skills know where to write the result. If the command is not found by its short name, type /setup and choose the row in the list that starts with the plugin's name.

The flow: from interview to implementation

An example task: write a PowerShell script that reports certificates that are about to expire or AD accounts that have been disabled. The task is the right size: it needs decisions that are worth making before code.

StepYou typeClaude does
1. Interview/mattpocock-skills:grilling and a description: "I want a script that reports certificates expiring within 30 days."Asks questions and proposes a recommended answer to each: which certificate stores, what the threshold is, where the report goes, whether the script may change anything. This is the plan before code.
2. Spec/mattpocock-skills:to-specGathers the conversation into a spec without a new interview and saves it to the ticket system you chose in the setup.
3. Tickets/mattpocock-skills:to-ticketsBreaks the spec into small tickets, each of which works from start to finish (for example "read one store and print a list"), and marks which ticket waits for which.
4. Clean context/clearEmpties the conversation. The spec and tickets are in files or in the tracker, so nothing is lost, and implementation starts without the interview's baggage.
5. Implementation/mattpocock-skills:implement #1Fetches the ticket, writes a test first (for example Pester), writes the code, runs the tests and reviews the change before the commit.
6. Next/clear, then /mattpocock-skills:implement #2The same round for the next ticket. One ticket, one commit.

Plan mode fits in like this: the interview and the spec are planning, so they can be done in plan mode (Shift+Tab), where Claude does not edit files. Implementation starts only when you approve. For a small fix the whole chain is too heavy: then ask for just a plan and continue.

Other useful skills from the same collection: tdd (test-driven development), code-review (review against the spec and the repo's conventions) and diagnosing-bugs (bug hunting).

Example: a complete starting prompt

The fifth, complete version of the coffee prompts from module 2. It is a good start for an interview (grilling): the decisions are made, and it asks for the rest to be asked.

Build a container under Portainer with a web interface built in Python, a SQLite database for history, and a postal code field in the settings. When I press a button, search for the cheapest coffee deals by that postal code, sorted by distance and price. Ask me for the missing details until we agree on the result. Base everything on facts, and if you don't know something, don't guess; say that you don't know.
Part of the promptWhat it does
"a container under Portainer"Says where the application runs: as a Docker container managed by Portainer. Claude can make a matching Dockerfile and start-up method.
"a web interface built in Python"Chooses the language and the shape of the application: a user interface in the browser.
"a SQLite database for history"Decides where the search history is stored. Claude knows what SQLite is.
"a postal code field in the settings"Decides how the location is given, and avoids guessing where you are.
"When I press a button, search for the cheapest coffee deals"Says what starts the search: a button, not a schedule.
"sorted by distance and price"Defines the order of the results.
"Ask me for the missing details until we agree"Asks for an interview before code: where the deals come from, what the distance limit is, what is stored. The same way as in the grilling skill.
"Base everything on facts, and if you don't know something, don't guess"Reduces guessing: Claude says it does not know, for example if it cannot find a suitable source of deal data.

Run /mattpocock-skills:grilling and give the prompt as the description, or give the prompt as it is without the skill. Answer the questions and continue only when the plan looks right to you.

Test-suite optimization and style alignment

Two tools that come with the course continue the same thinking. Both installation guides and the full content are in module 10.

  • optimize-testsuite measures a project's test suite, cuts the unnecessary delay the measurements show, proves the suite stays stable and reports before/after times. Use it when the tests are slow. Copyable: optimize-testsuite in module 10.
  • align-style compares a project's instructions (CLAUDE.md, git files, settings) with the way of working on this page, finds conflicts, duplicates and stale information, asks about every decision and carries the changes through. Use it when you adopt the way of working in an existing project. Copyable: align-style in module 10.
Always run these on a branch that can be discarded, and read the proposed changes before approving.

# Coding style

How I want Claude Code to work with me, with the reason behind each rule. My global `CLAUDE.md` imports this file,
so every session reads it. A project's own `CLAUDE.md` adds to these rules or overrides them for that project.

## Workflow

- **Plan before code.** For anything non-trivial, explain the approach first: the options, a recommendation, the
  files it touches. Write code only after I say "proceed". *Why: a wrong approach found in the plan costs a minute;
  found in the code it costs an hour.*
- **Small steps.** One change, one check, then the next change. *Why: a small diff is easy to review and easy to undo.*
- **No guessing.** When a path, version, setting, credential or name is unknown, look it up in the repo or ask me.
  *Why: a confident guess looks exactly like a fact.*
- **Stay in scope.** Fix what was asked. No unrequested refactoring, renames or clean-ups. *Why: unrelated changes
  hide the real change in the diff.*

## Questions

- Ask instead of guessing. Put several independent questions in one round, each with a recommended answer first.
- Never answer your own question and carry on as if I had decided.
- Answer my direct questions in the reply, not only inside a plan or a file.

## Verification

- **Test first.** Every new behaviour and every confirmed bug gets a test that fails without the change. Run it, see it
  fail, then make it pass. *Why: a test that never failed may not test anything.*
- **Check before "done".** Before saying a change is finished, run the tests and the checks you can reach yourself and
  report what was run and what was not. Never write "verified" or "works" for something that was not run.
- **Test plan.** When something needs me (a login, hardware, a judgement by eye), give numbered steps with the exact
  commands and the expected result of each step.
- **Read before you call.** Read a function's definition before calling or changing it; never assume its parameters
  or what it returns.

## Git

- **Short commits.** One short line per commit message, in English, imperative: `Fix login timeout`,
  `Add CSV export`. One logical change per commit.
- **Commit and push are separate steps.** Push only when I ask or when the project's rules say so.
- **Never commit secrets:** passwords, API keys, tokens, `.env` files, private keys, customer data. If one gets
  tracked, stop and tell me; removing it from history is my decision.
- **Look before you overwrite.** Check what a file holds before deleting or replacing it; never force-push without
  asking.

## Code

- **Comments explain why, not what.** Add one only for a hidden constraint, a workaround or a surprising rule.
- **Never fail silently.** A failed read, request or parse is shown or allowed to surface; it is never swallowed or
  counted as success.
- **Minimal scope.** No feature flags, compatibility layers or abstractions the task does not need.

## Safety

- **No secrets in chat, plans, memory or commits.** Refer to where a secret lives (a file name, a vault entry), never
  to its value.
- **Ask before destructive actions:** deleting files, dropping data, changing permissions, anything that cannot be
  undone. Also ask before adding, removing or weakening a confirmation step.
- **Follow my organization's rules** on what data may be given to an AI service. When unsure, ask me first.

## Communication

- Short and direct: one or two sentences per update, no long summary at the end.
- No emoji.

# Global instructions

These apply to every project. The full rule set with the reasons is imported here:

@~/.claude/coding-style.md

## Always

- Plan before code: explain the approach and wait for "proceed" before writing code for anything non-trivial.
- Ask instead of guessing; put questions to me with a recommended answer first.
- Test first: a new behaviour or a fixed bug gets a test that fails without the change.
- Check before "done": run the tests and say what was run and what was not.
- Commit messages are one short English line. Never commit secrets.
- Answer me in the language I write in. No emoji.

Exercises

1. Install the plugin and set up a repo

Requires: a Pro plan and Git for Windows. No Pro? Follow the instructor's demo (Max) or work with a partner.

Install mattpocock-skills, make a new folder, run git init and start claude. Run /setup-matt-pocock-skills and choose local markdown files as the tracker.

Show example answer

When you type /, the list has rows in the form /mattpocock-skills:.... The setup asks for the tracker, the labels and the place for documentation and writes the answers to the repo (typically to the CLAUDE.md file and the docs/ folder). Check the result with git status: the new or changed files are visible, and you can read them before committing.

2. From interview to tickets

Requires: a Pro plan and the repo from exercise 1. No Pro? Follow the instructor's demo (Max) or work with a partner.

Run /mattpocock-skills:grilling and describe the task: a PowerShell script that lists AD accounts that are disabled but still have group memberships. Answer the questions and then run to-spec and to-tickets. Read the tickets.

Show example answer

A good result has a spec and 3-5 tickets, for example: (1) list the disabled accounts, (2) add the group memberships, (3) export to CSV, (4) scheduling. The first ticket already produces a small working report. If a ticket is just "write everything", ask Claude to split it. Record in the spec, as a limit, that the script only reads and changes nothing.

3. Implement one ticket

Requires: a Pro plan and the tickets from exercise 2; it is good to have the Pester module installed. No Pro? Follow the instructor's demo (Max) or work with a partner.

Run /clear and then /mattpocock-skills:implement #1 (or the ticket's number). Watch whether Claude writes the test first, and finally check git diff and git log --oneline.

Show example answer

Claude fetches the ticket, writes a failing test, writes the code, runs the tests and proposes a short commit message. If the tests were not run, Claude must say so directly: ask "What did you run and what did you not?" If Active Directory is not available, the tests use example data. Do not let Claude run the script against the real AD without reading the command.

Optional: adopt the way of working permanently

  • Global instructions: the Copyable at the end of the page gives you the coding-style.md base and a CLAUDE.md that brings it into all your sessions. Edit the rules to be your own: remove the ones you do not want and add your own.
  • A project-specific CLAUDE.md adds rules or overrides the global ones only for that project (module 7).
  • Keep the list short: every rule consumes context in every session. Remove a rule that Claude follows anyway.
  • align-style brings an existing project into line: see module 10.
