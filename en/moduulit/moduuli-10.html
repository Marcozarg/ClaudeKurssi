What you need and what you do not

This module covers four ways of extending Claude Code: hooks, MCP servers, subagents and your own skills and commands. Let us say it straight: a beginner does not need any of them. The basics from modules 1-8 go a long way, and every addition is also more to maintain and more places where something can go wrong.

Try without them first, and add one only when you notice you are doing the same thing by hand for the third time. At the end of the page there are ready-made Copyables: install only the ones for which you recognize a need.

The module 9 Copyable coding-style is the foundation for the tools on this page: align-style reads it. See the installation in module 9.

The prerequisites in each Copyable's table are the same as in its manifest.json file. Where to get them: Claude Code from module 6, PowerShell 7 with the command winget install Microsoft.PowerShell, Python 3 with pytest from the project's own virtual environment, Matt Pocock's skills plugin from module 9, OpenAI Codex CLI with the command npm install -g @openai/codex, and the plan-review and review-intake commands from this page.

Tested: Claude Code 2.1.318, PowerShell 7.6.9, Python 3.14.7, Windows 11, November 2026 (11/2026). With other versions the behaviour may differ.

Hooks

A hook is a command that Claude Code runs by itself at a certain point: for example when a session starts (SessionStart), before a tool is used or when you send a prompt. A hook is not a request to Claude but the execution of a program, and it always works the same way. It suits things that must happen every time: a check, a log entry, printing the state of things.

Hooks are set in the file %USERPROFILE%\.claude\settings.json (all projects) or in the project's file .claude\settings.json. Hooks from different levels are combined. The text a SessionStart hook prints is added to Claude's context, which is why it must be fast.

A hook runs code on your machine with your own permissions. Read every hook before adding it, like any command.

The hooks on this page are in two Copyables: optimize-testsuite and routing. They are pasted into the settings.json file by hand, because the file is personal and should not be overwritten.

Source: code.claude.com/docs/en/hooks

MCP servers

MCP (Model Context Protocol) is an open standard for connecting Claude to external systems: task tracking, a database, monitoring or an API. Once a server is connected, Claude can read and act in the target system directly instead of you pasting information into the conversation.

A server is added with the command claude mcp add. You see the list with the command claude mcp list and the state in a session with the command /mcp. Visibility depends on the scope: local (only you, this project), project (.mcp.json, shared in version control) or user (all your projects).

Connect only servers you trust. A server that fetches external content can expose Claude to prompt injection (text that tries to steer it). Check what permissions you give.

You can often manage without MCP: Claude can run command-line tools (such as gh, module 8), and in module 5 you saw claude.ai's ready-made connectors. Add an MCP server only when you need a system that has no command-line tool.

Source: code.claude.com/docs/en/mcp

Subagents

A subagent is a specialized helper to which Claude hands a task. It has its own window, its own instructions, its own tools and often a different model. The benefit: long output (search results, logs) stays out of the main conversation, and only a summary returns to Claude.

A subagent is a Markdown file that begins with a YAML header: name, description (says when Claude uses it), tools and model. The file is saved in the folder %USERPROFILE%\.claude\agents\ (all projects) or in the project's folder .claude\agents\. Claude Code also has ready-made subagents, such as Explore (fast search) and Plan (for plan mode).

A beginner does not need to write their own. The Copyable routing contains three ready-made examples from which you can see the structure.

Source: code.claude.com/docs/en/sub-agents

Skills, commands and plugins

A skill is a folder that contains a file SKILL.md. Claude loads it when it fits the situation, or you call it yourself by typing /skill-name. A personal skill is in the folder %USERPROFILE%\.claude\skills\<name>\, a project's own in .claude\skills\. The folder can also hold supporting files, such as scripts.

A custom slash command is a single Markdown file in the folder %USERPROFILE%\.claude\commands\: the file done-check.md creates the command /done-check. According to the documentation, commands have been merged into skills: old command files still work, and if the same name has both a skill and a command, the skill wins. Skills are recommended for new ones. The commands on this page are single files for the sake of simplicity.

A plugin packages skills and other parts for sharing. A plugin's skills are named in the form /plugin-name:skill-name so they do not collide with your own. They are managed with the command /plugin.

Sources: code.claude.com/docs/en/skills and code.claude.com/docs/en/slash-commands

Model routing

Different models cost different amounts. Searching, running tests and implementing a clear ticket do not usually need the most expensive model, whereas planning, difficult debugging and the final check do. Model routing means the main session stays the planner and hands suitable work to a cheaper agent.

AgentModelTask
scoutHaiku, low effortSearch across many files; returns paths and line numbers
runnerHaiku, low effortRunning tests and builds; returns the errors as they are
implementerSonnet, medium effortImplementing one well-defined ticket with its tests

The command /routing controls the whole:

  • /routing on: turns routing on; the output contains the rule that Claude follows until the end of the session.
  • /routing off: stops delegation in this session.
  • /routing status: tells the state on one line.
  • /routing report: shows the cost tables and says what stands out.

The SessionStart hook prints the rule at the start of a new session only when routing is on. When it is off, the hook is silent and adds nothing to the context. Routing is worthwhile only when the agent's model is cheaper than the session's model: in a Sonnet session implementer is not worthwhile, but a Haiku search still is. If an agent's result does not pass the check, the work is redone at a higher level and the problem is recorded.

Remove unnecessary lines

Claude goes through the skills sentence by sentence, deletes the sentences that Claude would have done anyway, and looks for overlapping skills. The prompt changes skills directly, so make a commit first.

Audit my skills for no-op lines.
For every sentence, ask: would Claude have done that anyway? If yes, delete the whole sentence. Rewrite any "don't" line as what I want instead.

Two ways to find unnecessary lines

A precise way and an aggressive way. This is not a prompt but guidance for you.

Precise
Go line by line. Remove the line you suspect is a no-op. Run it again. And if the output didn't change, it was never doing anything in the first place.
Aggressive
(Which I personally prefer), is just have Claude scan the whole thing for no-op language and delete those words, then just see what happens.

Shorten the skills

Claude proposes a shorter version for each skill and marks the ones that are worth making invoked only by you (disable-model-invocation: true). Nothing is changed before you approve.

Simplify my existing skills.

Then flag which skills are good candidates to make user-invoked only: ones I'd rather call myself than have you fire on your own. For those, set disable-model-invocation: true in the frontmatter.

This is not a prompt but a way of working.

1. Run your skill on real work, not test cases.
2. Analyze chat history to fix recurring corrections.
3. Once you have that fix, stop and try again.

---
name: done-check
description: Pre-delivery verification before reporting a code change as finished - map every request point to a change, parse and test what changed, trace user-visible paths, grep for leftovers, apply the project's own checklist, and report what was and was NOT verified with a test plan. Run automatically before saying a code change is done, and when the user types /done-check.
---

Run before reporting a code change as finished, and before commit and push.

## Steps
1. **Request coverage:** list every point of the user's request (all of them, not just the last). Each maps to a change
   or an explicit "not done - why". For a ticket, re-read the ticket and its parent spec and make a checklist of every
   acceptance criterion and every UI behaviour it implies (open and close, empty, error and disabled states). Mark each
   item with the specific test that covers it or the manual check that was run; flag every item with neither as
   UNVERIFIED in the report.
2. **Build:** parse or compile every changed code file with the project's real toolchain (for example the PowerShell
   parser for .ps1 files, the compiler or linter for other languages).
3. **Tests:** run the tests that cover the changed code. Every new behaviour and confirmed bug has a test that fails
   without the change. A failing test is reported with its output, never hidden or re-run to see if it passes.
4. **Diff review:** for a change over about 50 lines, or one that touches storage, security or data formats, read the whole
   diff once more (or run a read-only review agent if the project has one) and fix confirmed problems before the final
   version bump.
5. **Trace:** for every user-visible change, follow the code path in the mode the user will actually test (first start on an
   empty environment, every language the UI has, the modes the project's CLAUDE.md names). A feature that is not
   reachable there is not done. For a screen change, look at a screenshot at desktop and phone width; a page that
   scrolls sideways is a bug.
6. **Leftovers:** Grep for old names, duplicate messages, debug output, texts or keys that no longer exist.
7. **Project items:** if the project has a checklist file (for example `.claude/checklists.md`), apply its "Before done"
   section, and its UI section when screen code or screen texts changed.
8. **Report** (short):
   - Done: what changed (one line per request point); for a ticket, the checklist from step 1 with its test or
     check per item and the UNVERIFIED ones.
   - I ran: which parse, tests, traces and test-plan steps ran, with results. Run every step you can reach first.
   - For you / NOT verified: only what needs the user (hardware, their login or a secret, a judgement by eye, a
     decision) or the real environment. A runnable check is never listed here. Never write "verified" or "works" for
     anything that was not actually run.
   - Test plan: numbered steps with exact copy-paste commands (full paths), expected result per step, cleanup, then the
     concrete next step.

name: plan-review
description: Self-review a plan before it is shown for approval - answer a fixed checklist (trust boundary, lifecycle, compatibility, automation, environment facts, failure handling, destructive actions, simplicity, scope, verification) plus the project's own plan items, write a Self-review section into the plan file and turn every gap into a question. Review the current plan before it is shown for approval.

## Procedure
1. Read the plan file. Answer every item below for THIS plan - check the code or the environment facts where an answer
   depends on them (CLAUDE.md, the repo, the machine), do not answer from memory.
2. If the project has a checklist file (for example `.claude/checklists.md`), answer its "Plan review" items too, and its
   UI items for plans that change screens or texts.
3. Write a `## Self-review` section at the end of the plan file: one line per item, `OK - <why>` or `GAP - <what>`.
   Items that do not apply: `n/a`.
4. Every GAP becomes a question to the user (independent ones in one round, recommended answer first) or a plan fix when
   the answer is obvious from the code. Update the plan with the answers before showing it for approval.

## Checklist
- **Trust boundary:** who can write each input the plan reads (files, directories, databases, packages, other tools)? Untrusted input
  validated? Secrets and keys stay where they belong? Every security claim no broader than what the code enforces?
- **Lifecycle:** first install on a fresh environment, upgrade from old versions, interrupted or partial runs, rerun
  (idempotent?), rollback, cancel at every confirmation. Cached or derived results invalidated when their source changes,
  and cleared only when verified, not when merely attempted.
- **Compatibility:** old and new versions side by side, mixed deployments, publish or deploy order.
- **Automate:** list every manual step the plan leaves to the user - can the script do it? Derive values from
  the environment (existing installation, machine name, config) instead of asking.
- **Environment facts:** hosts, rights, server editions, who creates what - taken from CLAUDE.md or the user, never assumed.
- **Failure handling:** unavailable dependencies (network share, database, mail, remote host) - retry, show it on screen,
  stop; no silent hang, no slow start.
- **Destructive actions:** anything that deletes, overwrites or removes a confirmation gate -> ask the user explicitly.
- **Simplicity:** fewer folders, steps, settings and screens for the user; no settings for things that should always
  happen.
- **Scope:** only what was asked; other files and scripts are reference-only; answers to the user's direct questions are
  stated in chat, not only in the plan.
- **Verification:** the plan names how each change is tested and what only the real environment can show.

name: review-intake
description: Process an external review the user pastes back (code review or plan review) - verify every finding against the code, fix confirmed bugs, ask about the rest, report a verdict table. The user has pasted review findings. Handle them with this procedure.

## 1. Classify
- **Code review** (findings about delivered code) or **plan review** (findings about a plan not yet implemented).
- If the user asks for a plan ("Plan for fixes", "Make plan for these", "Are these relevant?"), enter plan mode and use the
  verdicts as the plan input instead of editing code.

## 2. Verify every finding
Number the findings as the reviewer did. For each one open the cited code (Grep for the symbol, Read a narrow range) and
check the reasoning against the current code, including callers and the paths the reviewer describes. Verdict:
- **Confirmed bug** - the failure scenario really happens.
- **Not a bug** - the reasoning does not hold (say why, with file:line).
- **Already fixed** - the current code no longer has it.
- **Behaviour change** - the "fix" would change what the user sees or how the program works.
- **Unclear** - cannot be decided from the code (needs the real environment); say what would decide it.

## 3a. Code review
- Fix every Confirmed bug directly, without asking about scope.
- Ask about each Not a bug / Behaviour change / Unclear item, one question per item (several in one round), recommended
  option first. Never silently skip one.
- Add a regression test for each confirmed bug when the project has tests.
- Run /done-check (tests, project rules), then raise the version once for the batch as the last edit if the project
  versions its releases: /release Steps 1-4 only (version source and CHANGELOG.md), never its Step 5.
- Do not commit or push until the user says so; say in the report that the changes wait, because the user tests review
  fixes first.

## 3b. Plan review
- Verify each point in the code (step 2), then ask about every resulting plan change separately (one question per
  change, independent ones in one round, recommendation first) before rewriting the plan. Rewrite the plan only after the answers.

## 4. Report
Start with the table, answer in chat (never only inside a plan file):

| # | Finding (short) | Verdict | Action | Test |
|---|---|---|---|---|

Then one line per open question or remaining risk.

## 5. Later rounds
When the same reviewer sends a new round, keep the previous table. A finding that comes back is **reopened**: say why the
first fix missed it (wrong path, partial fix, missing test) before fixing it again.

# optimize-testsuite

What this produces: before/after medians of comparable full runs, each change with the gain it showed before it was applied, a
stability result and an accepted baseline. The project changes only on approval, one change at a time.

`ts` below is `& $HOME\.claude\skills\optimize-testsuite\testsuite.ps1`, called from PowerShell (a list such as
`-RunnerArgs @('-q', '-n', '12')`). It writes one report per run to `$HOME\.claude\test-suite-metrics\<hash of root>\`:
`<id>.summary.json`, `<id>.cases.json` (per test: outcome and setup, call, teardown seconds) and `<id>.log`. Nothing is written
into the project. A run is stopped at `-TimeoutSec`, else at the larger of the default (600 s) and three
times the median of the last three runs. `measure` stops at the first run that is not clean.

## 1. Baseline

Take the full-suite command from the project's CLAUDE.md and run it; measuring changes nothing in the project.

- pytest from `<root>\.venv`: `ts measure -Root <root> -RunnerArgs '-q' -Repeat 3` (`-RunnerArgs` = what the project writes after
  `pytest`; a partial run adds `-Selection focused`). Without that venv, pass `-Python <path to python.exe>`; the
  interpreter needs pytest.

Done when three runs are `completed` with exit 0 and `ts status -Root <root>` shows a recent median. A failed or timed-out run is
a finding: go to step 6. A run is never repeated to get a pass.

## 2. Find the cost

From the newest `cases.json`: seconds per phase, per file, and the twenty slowest tests. Decide which shape it is: a few slow
tests, or overhead times N (median setup per test times the number of tests). For pytest read
`$HOME\.claude\skills\optimize-testsuite\python.md` first. Done when the three largest costs are named with their seconds.

## 3. Prototype

Measure what each candidate would save with the project untouched (python.md: outside plugin, process split). Done when every
candidate has a measured gain or is dropped.

## 4. Change

One AskUserQuestion, multi-select: every candidate with its measured gain, the marked test that keeps running the real path, and
the effect on isolation. Apply and measure the chosen ones one at a time. Speed comes from setup, fixtures, waits and shutdown;
every test case stays unless the user approves its removal by name. Build it by the project's own rules.

## 5. Stability

`ts measure -Root <root> -RunnerArgs <the same as step 1> -Repeat 5`, then one run in shuffled order (python.md) with
`-Selection focused`, so it never mixes into the full runs. Done when all five are `completed` with exit 0 and the same number of
tests as the baseline or more. A hang, timeout or failure goes to step 6, and no gain is reported from a suite that is not stable:
faster setup changes timing and exposes races that were always there.

## 6. Defect found

Stop optimizing. Show the evidence: the failing output or the stack dump in `<id>.log`. Ask with AskUserQuestion:

- fix it now with a regression test in its own commit (recommended), then start again at step 1 for a new baseline;
- or record it and end: report the evidence, the before numbers and "stability not reached", without accept-baseline. Done when
  that report is given.

## 7. Report and baseline

A before/after table (median, range, number of tests, seconds per phase), every test id present before and absent after (expected:
none), and what was not measured (CI, other machines). In the same AskUserQuestion as the report, ask to accept the new baseline,
then `ts accept-baseline -Root <root>` (it prints its three source runs); `-AllowFewerTests` only for removals the user approved.
Done when `ts status -Root <root>` shows the baseline accepted in this run.

## Notes

- A "Test-suite advisory" comes from the daily hook (`ts evaluate`), which only reads reports. It advises when the median of the
  last three comparable full runs is over 60 s, or 25 percent and 10 s over the baseline, once per project per day; an accepted
  baseline counts as advised at its median.
- Runs are comparable when the command, runner version, runtime and number of pytest-xdist workers match and the number of
  tests, and of skipped plus xfailed tests, differs by at most max(5, 5 percent). A run with no counted tests is not valid.
  `ts status -Root <root>` says why runs are not compared; a slow advisory says when the regression check is off.

# pytest: finding and proving the cost

Reference for steps 2, 3 and 5 of optimize-testsuite. `<py>` is `<root>\.venv\Scripts\python.exe`, run from `<root>`.

## Where the time goes

`cases.json` rows are `[nodeid, outcome, setup, call, teardown]`. Totals per phase, per file and the slowest tests:

```powershell
$c = Get-Content <id>.cases.json -Raw | ConvertFrom-Json
'setup {0:n1}  call {1:n1}  teardown {2:n1}' -f ($c | % { $_[2] } | measure -Sum).Sum, ($c | % { $_[3] } | measure -Sum).Sum, ($c | % { $_[4] } | measure -Sum).Sum
$c | group { ($_[0] -split '::')[0] } | % { [pscustomobject]@{ file = $_.Name; n = $_.Count; s = [math]::Round(($_.Group | % { $_[2] + $_[3] + $_[4] } | measure -Sum).Sum, 1) } } | sort s -Descending | select -First 10
$c | sort { $_[2] + $_[3] + $_[4] } -Descending | select -First 20 | % { '{0,6:n2}  {1}' -f ($_[2] + $_[3] + $_[4]), $_[0] }
```

A flat list with a median setup of a few hundredths of a second means overhead times N: look at what every test's fixture does
(app start, migrations, key derivation, client start), not at single tests.

## The profiler trap

cProfile charges the time of a generator fixture to the frames that span its `yield`, and sees only the main thread. In
one project it showed 20 s of teardown where the phase durations showed 1 s. Trust the phase seconds in `cases.json`, then time
the suspect alone in a ten-line script (create the app, start the client, log in, one request: each on its own).

## Measuring a gain with the project untouched

- **Outside plugin.** Put the shortcut in a module outside the repo and load it:
  `$env:PYTHONPATH = '<scratchpad>'; & <py> -m pytest -q -p my_shortcut`. The module patches what the change would patch (for
  example replaces a start function with one that copies a prepared database) and the run shows the saving before any approval.
  Tests that fail under the prototype show which ones need the real path.
- **Process split** estimates parallel gain without installing anything: split the test files over N processes
  (`Start-Process` per group, wait for all) and take the wall time. It also shows whether tests share ports or files.
- **Order check.** A module with `pytest_collection_modifyitems` that reverses or shuffles `items` (seeded), loaded with `-p`,
  shows order dependence. Run it before and after a change that touches fixtures.

## Hangs

`ts measure` runs with `faulthandler_timeout=45` and kills the process tree at its own timeout, so `<id>.log` holds the stack of
every thread at the moment a test sat for 45 s. A thread standing in application code under an event loop frame is spinning, not
waiting. The venv launcher starts a second `python.exe`; a kill by hand needs `taskkill /PID <pid> /T /F`.

Faster setup exposes races that were always there: a busy loop in a job-draining function (an
`await gather(...)` over tasks that had all ended never yields) became 2 hangs in 5 runs, first on the fourth; in
another project xdist exposed three tests reading state a background loop had not written yet. That is why step 5 repeats.

## What has worked

| Pattern | Real path kept by | Gain |
|---|---|---|
| Cheap test-only cost (scrypt at production cost twice per test, lowered by a fixture) | a `real_hash` test checks production parameters | 160 s -> 56 s |
| Prepared state copied per test (a once-per-session migrated database, not 21 ms of migration each) | startup and migration modules marked `fresh_database` | 55 s -> 42 s |
| Routes built once per run (FastAPI 0.142 rebuilds every route per new app, 0.45 ms each, seen as slow calls; patch `_EffectiveRouteContext.from_api_route` in conftest) | login tests marked `fresh_routes` | 41.5 s -> 27.3 s |
| Server shutdown polls: `serve_forever(poll_interval=0.01)` in test servers (default waits up to 0.5 s) | n/a | per server stop |
| pytest-xdist `addopts = "-n auto"` when there is no setup to cut; one file runs with `-n 0` (workers start in about 10 s) | n/a | 138 s -> 27 s on 12 threads |

The route cost was found by timing one page alone (10 ms against 1 ms for the others) and profiling that request.

## What costs more than it gives

- One app object shared across tests: needs a production change and puts shared state between tests.
- Folding parametrized cases into one test: saves setup, loses the failing case's name.
- pytest-xdist: the largest gain left once setup is lean, and a dependency plus a CI change. It is its own decision for the user.
- Windows takes about 2 s to refuse a connection to a closed local port; tests that need a refused connection cost that there.

function Get-Git([string]$CanonicalRoot) {

    if ($LASTEXITCODE -ne 0) { return @{ revision = $null; dirtyFiles = $null } }

function Invoke-Child([string]$Exe, [string[]]$Arguments, [string]$WorkDir, [hashtable]$Environment, [int]$Seconds, [string]$LogPath) {
    $info = [System.Diagnostics.ProcessStartInfo]::new($Exe)
    foreach ($a in $Arguments) { $info.ArgumentList.Add($a) }
    $info.WorkingDirectory = $WorkDir
    $info.UseShellExecute = $false
    $info.RedirectStandardOutput = $true
    $info.RedirectStandardError = $true
    foreach ($name in $Environment.Keys) {
        if ($null -eq $Environment[$name]) { [void]$info.Environment.Remove($name) } else { $info.Environment[$name] = $Environment[$name] }
    }
    $clock = [System.Diagnostics.Stopwatch]::StartNew()
    $process = [System.Diagnostics.Process]::Start($info)
    $stdout = $process.StandardOutput.ReadToEndAsync()
    $stderr = $process.StandardError.ReadToEndAsync()
    $timedOut = -not $process.WaitForExit($Seconds * 1000)
    if ($timedOut) {
        # The venv launcher starts the real interpreter as a child, so the whole tree goes.
        & taskkill /PID $process.Id /T /F 2>&1 | Out-Null
        $process.WaitForExit()
    }
    $clock.Stop()
    Set-Content -LiteralPath $LogPath -Value ($stdout.Result + $stderr.Result) -Encoding utf8
    @{ timedOut = $timedOut; exitCode = $process.ExitCode; seconds = [Math]::Round($clock.Elapsed.TotalSeconds, 2) }
}

function Get-Timeout([string]$ProjectDir, [string]$Runner, [string]$RunSelection) {
    if ($TimeoutSec -gt 0) { return $TimeoutSec }
    # Earlier runs only raise the limit: they may come from another interpreter or a much smaller suite.
    $walls = @(Get-Summaries $ProjectDir | Where-Object { (Test-Valid $_) -and $_.runner -eq $Runner -and $_.selection -eq $RunSelection } |
        Select-Object -First 3 | ForEach-Object { [double]$_.wallSeconds })
    if ($walls.Count -lt 3) { return $DefaultTimeoutSec[$Runner] }
    [int][Math]::Max($DefaultTimeoutSec[$Runner], 3 * (Get-Median $walls))
}

function Measure-Pytest([string]$CanonicalRoot, $Entry) {
    $exe = if ($Python) { $Python } else { Join-Path $CanonicalRoot '.venv\Scripts\python.exe' }
    if (-not (Test-Path -LiteralPath $exe)) { throw "No Python interpreter at $exe; pass -Python." }
    $dir = Get-ProjectDir $Entry
    $started = [datetime]::UtcNow
    # Milliseconds keep the ids of one process in run order; the two random digits separate two processes.
    $id = '{0}{1}' -f $started.ToString('yyyyMMdd-HHmmss-fff'), [guid]::NewGuid().ToString('N').Substring(0, 2)
    $summary = New-Summary $id $started $CanonicalRoot 'pytest' (@('python', '-m', 'pytest') + $RunnerArgs) $Selection
    $summary.log = "$id.log"
    $n = [Array]::IndexOf($RunnerArgs, '-n')
    if ($n -ge 0 -and $n + 1 -lt $RunnerArgs.Count) { $summary.workers = $RunnerArgs[$n + 1] }
    $git = Get-Git $CanonicalRoot
    $summary.revision = $git.revision
    $summary.dirtyFiles = $git.dirtyFiles

    $out = Join-Path $dir $id
    $arguments = @('-m', 'pytest') + $RunnerArgs + @('-p', 'tsm_report', '-o', 'faulthandler_timeout=45')
    $environment = @{ TSM_OUT = $out; PYTHONUNBUFFERED = '1'
                      PYTHONPATH = (@($PSScriptRoot, $env:PYTHONPATH) | Where-Object { $_ }) -join ';' }
    $summary.timeoutSec = Get-Timeout $dir 'pytest' $Selection
    $run = Invoke-Child $exe $arguments $CanonicalRoot $environment $summary.timeoutSec (Join-Path $dir "$id.log")

    $pluginPath = "$out.plugin.json"
    if ($run.timedOut) {
        $summary.status = 'timeout'
    }
    elseif (Test-Path -LiteralPath $pluginPath) {
        $plugin = Read-Json $pluginPath
        $summary.status = 'completed'
        $summary.wallSeconds = $run.seconds
        foreach ($name in 'runnerVersion', 'runtime', 'membership', 'collected', 'phases', 'workers') { $summary[$name] = $plugin[$name] }
        foreach ($name in 'passed', 'failed', 'skipped', 'xfailed', 'xpassed') { $summary[$name] = $plugin.counts[$name] }
        $summary.errors = $plugin.counts.error
    }
    if (-not $run.timedOut) { $summary.exitCode = $run.exitCode }
    Remove-Item -LiteralPath $pluginPath -Force -ErrorAction SilentlyContinue
    Write-Json "$out.summary.json" $summary
    $summary
}

function Format-Tests($Runs) {
    $counts = @($Runs | ForEach-Object { [int]$_.collected } | Sort-Object)

function Test-Comparable($A, $B) {
    if ((Get-Key $A) -ne (Get-Key $B)) { return $false }
    if ($A.membership -eq $B.membership) { return $true }
    $tolerance = Get-Tolerance $A.collected $B.collected
    [Math]::Abs($A.collected - $B.collected) -le $tolerance -and
        [Math]::Abs(($A.skipped + $A.xfailed) - ($B.skipped + $B.xfailed)) -le $tolerance
}

function Test-Trio($Runs) {
    (Test-Comparable $Runs[0] $Runs[1]) -and (Test-Comparable $Runs[0] $Runs[2]) -and (Test-Comparable $Runs[1] $Runs[2])
}

function New-Baseline($Runs, [string]$By, [string]$Day) {
    [ordered]@{
        ids = @($Runs | ForEach-Object { $_.id })
        median = Get-Median ($Runs | ForEach-Object { [double]$_.wallSeconds })
        collected = [int](Get-Median ($Runs | ForEach-Object { [double]$_.collected }))
        skipped = [int](Get-Median ($Runs | ForEach-Object { [double]($_.skipped + $_.xfailed) }))
        runsUntil = Get-Day (ConvertTo-Utc $Runs[2].startedUtc); setOn = $Day; by = $By
    }
}

function Read-State([string]$ProjectDir, $Entry) {

function Get-Standing($Entry, $State, [datetime]$NowUtc) {
    # One record per kind of full run: what the recent runs say against the baseline.
    $runs = @(Get-Summaries (Join-Path $StateDir $Entry.hash) | Where-Object { $_.selection -ne 'focused' } |
        Sort-Object { ConvertTo-Utc $_.startedUtc })
    foreach ($group in $runs | Group-Object { Get-Key $_ }) {
        $valid = @($group.Group | Where-Object { Test-Valid $_ })
        $baseline = $State.baselines[$group.Name]
        for ($i = 0; -not $baseline -and $i + 2 -lt $valid.Count; $i++) {
            if (Test-Trio $valid[$i..($i + 2)]) { $baseline = New-Baseline $valid[$i..($i + 2)] 'first-trio' (Get-Day $NowUtc) }
        }
        $standing = @{ key = $group.Name; selection = $group.Group[0].selection; runner = $group.Group[0].runner; runs = $valid.Count
                       baseline = $baseline; recent = $null; median = $null; note = $null; reasons = @() }
        $last = @($valid | Select-Object -Last 3)
        if ($last.Count -lt 3) {
            $standing.note = 'three completed runs are needed'
        }
        elseif (($NowUtc - (ConvertTo-Utc $last[0].startedUtc)).TotalDays -gt $RecentDays) {
            $standing.note = "no three runs in the last $RecentDays days"
        }
        elseif (-not (Test-Trio $last)) {
            $standing.note = "the last three runs are not comparable: $(Format-Tests $last)"
        }
        else {
            $standing.recent = $last
            $standing.median = Get-Median ($last | ForEach-Object { [double]$_.wallSeconds })
            if ($Entry.slowRule -and $standing.median -gt $SlowSeconds) { $standing.reasons = @('slow') }
            if ($baseline) {
                $collected = [int](Get-Median ($last | ForEach-Object { [double]$_.collected }))
                $skipped = [int](Get-Median ($last | ForEach-Object { [double]($_.skipped + $_.xfailed) }))
                $tolerance = Get-Tolerance $collected $baseline.collected
                if ([Math]::Abs($collected - $baseline.collected) -gt $tolerance -or [Math]::Abs($skipped - $baseline.skipped) -gt $tolerance) {
                    $standing.note = "the baseline of $($baseline.collected) tests is no longer comparable; accept a new one"
                }
                elseif ($standing.median -gt $WorsePercent * $baseline.median -and $standing.median - $baseline.median -gt $WorseSeconds) {
                    $standing.reasons = @('regression') + $standing.reasons
                }
            }
        }
        $standing
    }
}

function Select-Advisory($Entry, $State, $Standings, [string]$Today) {
    $candidates = foreach ($standing in $Standings) {
        foreach ($reason in $standing.reasons) {
            $last = if ($State.advised[$standing.key]) { $State.advised[$standing.key][$reason] }
            $again = $last -and $standing.median -gt $WorsePercent * $last.median -and $standing.median - $last.median -gt $WorseSeconds -and
                ([datetime]$Today - [datetime]"$($last.day)").TotalDays -ge $CooldownDays
            if (-not $last -or $again) { @{ standing = $standing; reason = $reason } }
        }
    }
    $chosen = @($candidates) | Sort-Object { $_.reason -ne 'regression' }, { -$_.standing.median } | Select-Object -First 1
    if (-not $chosen) { return $null }
    $standing = $chosen.standing
    if (-not $State.advised[$standing.key]) { $State.advised[$standing.key] = @{} }
    $State.advised[$standing.key][$chosen.reason] = @{ day = $Today; median = $standing.median }

    $name = Split-Path -Leaf $Entry.root
    $runs = "the median of the last three comparable $($standing.selection) runs is $(Format-Seconds $standing.median)"
    $span = "$(Format-Tests $standing.recent), $(Get-Day (ConvertTo-Utc $standing.recent[0].startedUtc)) to $(Get-Day (ConvertTo-Utc $standing.recent[2].startedUtc))"
    $finding = if ($chosen.reason -eq 'regression') {
        $over = $standing.median - $standing.baseline.median
        "regression: $runs, $(Format-Seconds $over) ($([int](100 * $over / $standing.baseline.median)) %) over the baseline of " +
            "$(Format-Seconds $standing.baseline.median) from $($standing.baseline.runsUntil) ($span)."
    }
    else {
        $off = if ($standing.note) { " Regression check off: $($standing.note)." } else { '' }
        "slow suite: $runs ($span), over the $SlowSeconds s mark.$off"
    }
    $text = "Test-suite advisory for ${name}: $finding In your next reply add one brief suggestion to run /optimize-testsuite " +
        'for this project; do not start it unasked.'
    $text.Substring(0, [Math]::Min($text.Length, 600))
}

"""pytest plugin of the optimize-testsuite skill: records what one run collected, each test's outcome and the seconds
of each phase. testsuite.ps1 loads it with -p and names the output in TSM_OUT; nothing is written into the project."""

import hashlib
import json
import os
import platform

import pytest

PHASES = ("setup", "call", "teardown")


class Report:
    def __init__(self, out: str):
        self.out = out
        self.ids: list[str] = []
        self.cases: dict[str, dict] = {}

    def pytest_collection_finish(self, session):
        self.ids = sorted(item.nodeid for item in session.items)

    # Under pytest-xdist the controller collects nothing itself; each worker reports the ids it collected.
    @pytest.hookimpl(optionalhook=True)
    def pytest_xdist_node_collection_finished(self, node, ids):
        self.ids = sorted(ids)

    def pytest_runtest_logreport(self, report):
        case = self.cases.setdefault(report.nodeid, {"outcome": None, **dict.fromkeys(PHASES)})
        case[report.when] = round(report.duration, 4)
        if hasattr(report, "wasxfail"):
            if report.skipped:
                case["outcome"] = "xfailed"
            elif report.passed and report.when == "call":
                case["outcome"] = "xpassed"
        elif report.failed:
            # A failure outside the test body is pytest's "error", and it outranks a passed call.
            case["outcome"] = "failed" if report.when == "call" else "error"
        elif report.skipped:
            case["outcome"] = "skipped"
        elif report.when == "call" and case["outcome"] is None:
            case["outcome"] = "passed"

    def pytest_sessionfinish(self, session, exitstatus):
        if hasattr(session.config, "workerinput"):
            return
        counts = dict.fromkeys(("passed", "failed", "skipped", "xfailed", "xpassed", "error"), 0)
        for case in self.cases.values():
            if case["outcome"] is not None:
                counts[case["outcome"]] += 1
        phases = {p: round(sum(c[p] or 0 for c in self.cases.values()), 3) for p in PHASES}
        with open(self.out + ".cases.json", "w", encoding="utf-8") as f:
            json.dump([[nodeid, c["outcome"], *(c[p] for p in PHASES)] for nodeid, c in sorted(self.cases.items())], f)
        with open(self.out + ".plugin.json", "w", encoding="utf-8") as f:
            json.dump({"collected": len(self.ids),
                       "membership": hashlib.sha256("\n".join(self.ids).encode()).hexdigest(),
                       "counts": counts, "phases": phases, "runnerVersion": pytest.__version__,
                       "workers": str(workers) if (workers := getattr(session.config.option, "numprocesses", None)) else None,
                       "runtime": platform.python_version()}, f)

        $a.input += $t.in; $a.output += $t.out; $a.cacheRead += $t.read; $a.cacheWrite += $t.w5 + $t.w1; $a.cost += $cost
        $runs[$key][$r.file] = $true
        if (-not $main) {
            $atMain = $cost
            if ($s.mainPrice) { $atMain = Get-Cost $s.mainPrice $t } else { $noMain[$r.session] = $true }
            $a.atMain = [double]$a.atMain + $atMain
            $a.saved = $a.atMain - $a.cost
        }

        $dayKey = $r.ts.ToString('yyyy-MM-dd')
        if (-not $byDay.ContainsKey($dayKey)) {
            $byDay[$dayKey] = [ordered]@{ date = $dayKey; mainCost = 0.0; agentCost = 0.0; totalCost = 0.0; tokens = 0L }
        }
        # The skill invoked last in the user's turn; a skill started inside another takes over.
        if (-not $bySkill.ContainsKey($r.skill)) {
            $bySkill[$r.skill] = [ordered]@{ skill = $r.skill; mainCost = 0.0; agentCost = 0.0; totalCost = 0.0; tokens = 0L }
        }
        if (-not $byState.ContainsKey($s.state)) {
            $byState[$s.state] = [ordered]@{ routing = $s.state; sessions = @{}; mainCost = 0.0; agentCost = 0.0; totalCost = 0.0; tokens = 0L }
        }
        $byState[$s.state].sessions[$r.session] = $true
        foreach ($row in $byDay[$dayKey], $bySkill[$r.skill], $byState[$s.state]) {
            if ($main) { $row.mainCost += $cost } else { $row.agentCost += $cost }
            $row.totalCost += $cost
            $row.tokens += $t.total
        }
    }
    foreach ($key in $runs.Keys) { $byAgent[$key].runs = $runs[$key].Count }
    foreach ($row in $byState.Values) {
        $row.sessions = $row.sessions.Count
        $row.perSession = $row.totalCost / $row.sessions
    }

    $problems = @($history | Where-Object { $_.event -eq 'problem' -and ([datetime]$_.ts).ToLocalTime() -ge $since })
    foreach ($a in $byAgent.Values) {
        $a.problems = @($problems | Where-Object { $_.agent -eq $a.agent }).Count
    }

    [ordered]@{
        since    = $since.ToString('yyyy-MM-dd')
        days     = $Days
        byState  = @($byState.Values | Sort-Object { $_.routing } -Descending)
        byDay    = @($byDay.Values | Sort-Object { $_.date })
        bySkill  = @($bySkill.Values | Sort-Object { -$_.totalCost })
        byAgent  = @($byAgent.Values | Sort-Object { -$_.cost })
        problems = $problems
        unpriced = @($unpriced.GetEnumerator() | ForEach-Object { [ordered]@{ model = $_.Key; tokens = $_.Value } })
        noMain   = @($noMain.Keys | Sort-Object)
    }
}

# Format-Table drops the last columns when the host is narrow, whatever Out-String -Width says.
function Show-Table([object[]]$Rows) {
    if ($Rows.Count -eq 0) { return }
    $names = @($Rows[0].Keys)
    $width = @{}
    foreach ($n in $names) {
        $width[$n] = (@($n.Length) + @($Rows | ForEach-Object { ([string]$_[$n]).Length }) | Measure-Object -Maximum).Maximum
    }
    ($names | ForEach-Object { $_.PadRight($width[$_]) }) -join '  '
    ($names | ForEach-Object { '-' * $width[$_] }) -join '  '
    foreach ($row in $Rows) { ($names | ForEach-Object { ([string]$row[$_]).PadRight($width[$_]) }) -join '  ' }
    ''
}
