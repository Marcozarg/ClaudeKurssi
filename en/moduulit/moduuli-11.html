Module 11 · Session 5

Debugging with Claude

Core ~30 minOptional ~15 minPro / Max

What to give Claude

"The script doesn't work" forces Claude to guess. The guess may land, but Claude often fixes something that was not broken. Give it three things instead:

  • Symptom: what happens and what you expected to happen. "The report lists every disk, even though D: has 15 % free."
  • The exact error message: the whole text, copied, not from memory. The line number and the error type often say more than an explanation.
  • Steps: which command and which input make the bug appear. Also the environment (PowerShell 5.1 or 7, Windows version) and what changed last.
Bug: <what happens>. I expected: <what should happen>.
The whole error message:
<paste here>
I reproduce it like this: <command and input>
Environment: <PowerShell version, operating system>. Last change: <what I changed>.
Find the cause first. Do not change the code before you tell me what causes the bug.

The last line matters: it keeps Claude debugging instead of letting it jump straight to a fix.

Reproduce the bug first

Before the fix you need a way to see the bug yourself: a command that gives the wrong result every time. Without it you do not know whether a change fixed anything. Ask Claude to build the reproduction before it touches the code:

Make the smallest command or script that shows this bug every time. Run it and show the output. Do not fix anything yet.

A good reproduction is fast and always the same. If the bug shows only sometimes, ask Claude to run the reproduction many times in a row and count how often it appears.

One hypothesis at a time

When Claude changes five things at once and the bug goes away, nobody knows which change helped and which four were useless or harmful. Ask for one suspected cause at a time:

  1. Claude lists the possible causes, most likely first.
  2. For each, it says how to check the suspicion without changing code (for example by printing an intermediate value).
  3. They are checked one at a time, and only a confirmed cause gets fixed.
List the three most likely causes. For each, say how to confirm it without changing code. We check them one at a time.

A failing test before the fix

Once the cause is found, ask first for a test that fails with the current code because of exactly this bug. Only then the fix. The test proves two things: the fix works, and the same bug does not come back unnoticed later.

Write a Pester test that fails with the current code because of this bug. Run it and show that it fails. Only then fix it and run the test again.
Check that the test really failed before the fix. A test that passes already before the fix does not test this bug.

Logs and stack traces, safely

Logs and stack traces are the best material for debugging, but they often hold usernames, server names, paths and sometimes passwords or tokens. The same rules as in module 0:

  • Replace names, addresses and paths with placeholders before pasting.
  • Paste only the lines that matter for the bug, not the whole log.
  • If a password or token shows in the log, change it. It has already leaked into the log.

In Claude Code, Claude can read the log file itself. The same limit applies: say which file it may read, and keep secrets out of its reach.

When to stop

If Claude has tried three fixes and none helped, the conversation is full of false leads, and the next attempt builds on them. Stop:

  • Ask Claude to write a short summary: what is known, what was tried and what was ruled out.
  • Run /clear and start a new conversation with the summary. A clean context also saves your usage limit.
  • Go back to the reproduction: does the bug still show with the same command?

If Claude made useless changes on the way, /rewind (module 7) undoes the file changes it made. Git (module 8) restores the rest.

The diagnosing-bugs skill

Matt Pocock's skill collection (module 9) has diagnosing-bugs, which follows the way of working above step by step: first a feedback loop that shows the bug, then hypotheses one at a time, a failing test and the fix. It also tells Claude to hide secrets in its output.

/mattpocock-skills:diagnosing-bugs The disk report lists every disk, even though D: has 15 % free.

The skill is most useful for hard bugs. A plain prompt is enough for a simple typo.

Exercises

1. Fix the disk report

Needs: a Pro subscription. No Pro? Paste the script and the symptom into a claude.ai chat (Free) and ask for the cause before the fix.

Save the script as disk-report.ps1 in a new folder. The script should list the disks with less than 10 % free. Run it with .\disk-report.ps1: it lists all three disks and claims each is 0 % free. Start claude in the folder and describe the bug with the template from "What to give Claude".

# disk-report.ps1: lists the disks whose free space is below the limit (percent)
param([int]$Limit = 10)
$disks = @(
    [pscustomobject]@{ Name = 'C:'; SizeGB = 256;  FreeGB = 20 }
    [pscustomobject]@{ Name = 'D:'; SizeGB = 1000; FreeGB = 150 }
    [pscustomobject]@{ Name = 'E:'; SizeGB = 500;  FreeGB = 45 }
)
foreach ($d in $disks) {
    $percent = [int]($d.FreeGB / $d.SizeGB) * 100
    if ($percent -lt $Limit) {
        "$($d.Name) only $percent % free"
    }
}
Show example answer

The cause is where the brackets are on the line $percent = .... [int] rounds the quotient (for example 20 / 256 = 0.078) to zero before the multiplication, so every disk is 0 % and below the limit. The fix: $percent = [int]($d.FreeGB / $d.SizeGB * 100). The fixed script prints C: only 8 % free and E: only 9 % free, not D: (15 %). A good Claude tells you the cause before the fix and shows an intermediate value, for example by printing the quotient before and after the [int] conversion.

2. A test before the fix

Needs: a Pro subscription and Pester (Windows PowerShell 5.1 has an old version; Install-Module Pester -Scope CurrentUser installs a new one). No Pro? Follow the instructor's demo (Max) or work with a partner.

Restore the original script from exercise 1 (or do this exercise first). Ask Claude with the prompt from "A failing test before the fix": the test first, show that it fails, then the fix. Check yourself that the test failed before the fix and passed after it.

Show example answer

Claude makes for example a file disk-report.Tests.ps1 that runs the script and checks that the output has C: and E: but not D:. The first run (Invoke-Pester) fails because D: is listed. After the fix the same test passes. If Claude fixed the script before running the test, ask it to restore the original and show the failing run: otherwise you do not know whether the test tests the right thing.

3. A good bug report

Needs: a Claude account (Free is enough), claude.ai.

A coworker writes: "The backup script is broken again, fix it." In claude.ai, write the message that would get you good help from Claude, with made-up details. Then ask Claude to rate your message: what is still missing?

Show example answer

A good message has the symptom and the expectation ("the run ends in an error, I expected a zip file in the target folder"), the whole exact error message, the command that reproduces the bug, the environment and the last change ("the password was changed on Monday"). It ends with a request to find the cause before the fix. Claude typically asks about what is missing: when the script last worked and whether the error comes every time.

Optional: performance and git bisect

  • Slow, not broken: measure before you change anything. Ask Claude to measure the time (Measure-Command { .\script.ps1 }) and find the slowest part, and compare the measurement before and after the change. Without a measurement, "faster" is a guess.
  • Which change broke it? If the bug appeared at some point in the history, git bisect finds the breaking commit by halving: you mark one good and one bad commit, and git walks the range. When the reproduction is a command, git bisect run <command> does the search by itself. Ask Claude: "Use git bisect to find the commit after which this test started failing."
  • A bug that comes and goes: run the reproduction in a loop and count the hits. A bug that shows every other run can be found; one that shows once in a hundred cannot yet.
  • Read more: git bisect and mattpocock/skills.
