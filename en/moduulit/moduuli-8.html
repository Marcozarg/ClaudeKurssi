Git and GitHub / GitLab

Core ~45 minOptional ~20 minPro / Max

Why git?

Git saves the history of your files: you can go back to an earlier version, compare changes and work in parallel safely. Claude can make many changes quickly, so git is your safety net. In module 7 you saw that /rewind does not track changes made by shell commands. Git tracks everything that has been saved.

Git is a tool on your machine. GitHub and GitLab are services where a repo (a code repository) can be stored and where work is tracked with issues and change requests.

You need Git for Windows (git --version works in the terminal). If it does not, install it from git-scm.com and open a new terminal.

The way of working: make changes on your own branch, check git diff, save a commit and only then send.

How Claude Code uses git

Claude Code runs git commands the same way as other commands and asks permission unless you have allowed them. Read-only commands (for example git status and git diff) usually go through without asking.

  • Viewing changes: "What have I changed? Tell me in plain English." Claude reads the diff and summarizes it.
  • Commit messages: "Make a commit with a message that describes the change." Claude checks the changes, chooses the files and writes the message.
  • Branches: "Create a new branch for this fix and make the change there."
  • Conflicts: "Help me resolve this merge conflict."
Always check the diff before committing, and ask for a push only when you are ready. Keep permanent permissions (module 7) deliberately narrow: git push and git reset --hard do not belong on the "allow always" list. Do not commit secrets (.env, passwords, keys).

Example prompts

Sign in first (gh auth login or glab auth login) and start claude in the repo's folder.

List the open issues and group them by topic. Tell me which ones look the most urgent.
Create an issue: "The backup script does not log errors". Add steps to reproduce and a proposed fix to the description.
Read issue 12, make the fix on your own branch, run the tests and make a commit. Do not push yet.
Make a pull request (GitHub) or merge request (GitLab) of the changes, with a description that says what was changed and why.

Note that the content of issues is text written by others. Claude reads it as part of the work, and the text may contain instructions that try to steer it. Check what Claude is about to run before you approve.

Publishing is a step that cannot be undone: git push, creating an issue and a pull request are visible to others. Keep these behind a permission prompt.

Exercises

1. Clone a repo and ask about its history

Requires: a Pro plan and Git for Windows. No Pro? Follow the instructor's demo (Max) or work with a partner.

Clone the course repo github.com/Marcozarg/ClaudeKurssi, start claude in the folder and ask: "Show the last 5 commits and tell me what each one changed."

Show example answer

Claude runs the command git log (for example git log -5 --stat) and tells you what each commit changed: which files were added or modified. This is reading, so Claude Code does not usually ask permission. Check the result yourself by running git log --oneline -5.

2. A script change on its own branch

Requires: a Pro plan and Git for Windows. No Pro? Follow the instructor's demo (Max) or work with a partner.

Make a new folder, run git init and add a PowerShell script that reads a CSV file of users (name, department, email) and removes empty rows and duplicates. Make the first commit. Then ask Claude: "Create a branch cleanup, add an email address check with a regex to the script and make a commit." Finally look at git log --oneline and git diff main.

Show example answer

Claude creates the branch (git switch -c cleanup), adds the check, for example in the form $email -match '^[^@\s]+@[^@\s]+\.[^@\s]+$', and makes a commit with a descriptive message. The diff shows only the added lines. If the main branch is named master, use the command git diff master. Test the regex yourself with example addresses: it is simple and does not accept everything that email addresses allow.

3. An issue with Claude (GitHub or GitLab)

Requires: a Pro plan, and a GitHub or GitLab account and a test repo where you may create issues. No Pro? Follow the instructor's demo (Max) or work with a partner.

Install gh or glab and sign in. Ask Claude to create an issue in the test repo: "Create an issue: 'Runbook: restarting the service'. In the description a checklist: check the status, stop, start, verify." Then ask it to list the open issues and close the issue you created.

Show example answer

Claude uses the command gh issue create (in GitLab glab issue create), lists the issues with gh issue list and closes the issue with gh issue close (glab issue close). Every command asks permission unless you have allowed it: read the command before approving. Check the result in the browser. Use a test repo, not a real working repo.

Optional: Projects, boards and a safe way of working

  • GitHub Projects: the gh project commands (for example item-list, item-add) require the project scope: gh auth refresh -s project. Ask Claude: "List the open tasks in the project and suggest which one to take next."
  • GitLab boards are based on labels: when an issue's label changes, it moves from one column to another. Ask: "Add the label 'In progress' to issue 12."
  • Limit the permissions: sign in with an account that has only the permissions needed, and test in a test repo first.
  • Fixing git mistakes: a wrong commit can usually be fixed, but pushed history should not be rewritten. Ask Claude for the options before you run commands with --force or reset --hard in their name.
  • Read more: gh issue and glab issue.
