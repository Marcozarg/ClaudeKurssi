A good prompt

Core ~55 minOptional ~30 minFree

A prompt is an assignment

A prompt is the message you use to give Claude a task. Think of it as giving a task to a new, capable colleague who knows nothing about your environment. What would they need to succeed the first time?

  • Goal: what you want to achieve and why
  • Context: the environment, versions, constraints, what you have already tried
  • Input: an error message, a log excerpt, a script or sample data
  • Format: what kind of answer you want: a script, a table, a short guide, three options

Context makes the difference

Weak

Write a script that deletes old users.

Better

Environment: Windows Server 2022, ActiveDirectory module, PowerShell 5.1.
Goal: find users who have not signed in for 120 days and DISABLE THEM (not delete).
Constraints: skip the OU "Service accounts" and accounts whose name starts with "svc-".
Format: a script with -WhatIf support that writes a CSV report before making changes.
At the end, tell me what I need to check before I run it in production.

The second one states the version, limits the risks and sets the format. The answer is almost always more useful, and it is easier to check.

Show an example

When you want a specific format, show it. One or two examples say more than a long explanation.

Turn these log lines into a table with the columns Time, Level, Service, Message.
Example of a wanted row:
| 08:14:22 | ERROR | spooler | Print job failed |

Lines:
2026-11-03T08:14:22 [ERROR] spooler: Print job failed
2026-11-03T08:15:01 [WARN] w32time: Time sync delayed
2026-11-03T08:15:40 [INFO] spooler: Service restarted

The same works with regexes: give a few lines that must match and a few that must not.

Iterate

The first answer is rarely final. Continue in the same conversation and steer:

  • "Shorten it by half and remove the explanations."
  • "The script fails with this error: ..." and paste the error as it is.
  • "Use PowerShell 5.1 features, not 7."
  • "Good, but do not use Write-Host, return objects."

If the conversation goes off track, go back and edit your earlier message instead of correcting afterwards. That way the wrong direction does not stay in the context.

Ask Claude to ask questions

When the task is large or unclear, Claude guesses the missing details. Prevent the guessing by asking it to ask first:

I want a guide for the helpdesk on creating accounts for a new employee.
Do not write the guide yet. First ask me the things you need to know,
one at a time, and give a recommended answer with each question.

Only when you have answered, ask for the guide. The same approach works for all planning, and it is the basis of the Claude Code way of working (module 9).

More techniques

A few more techniques from Anthropic's guidance that work in almost any prompt:

  • Put pasted material inside tags, for example <log>...</log>. Then Claude keeps the data apart from the instructions.
  • Allow "I don't know". Say for example "if the information is not enough, say so". It reduces made-up answers.
  • For a long document, ask for quotes first. Ask Claude to quote the relevant parts and answer only from those quotes.
  • Material first, question last. With long material the answers can improve by up to 30 %.
  • Say what you want, not what you do not want. "Do not use markdown" -> "write flowing paragraphs".
  • Give a one-line role, for example "You are an experienced Windows administrator." Even a single sentence makes a difference.
  • Split a big job into numbered steps when order or completeness matters, for example a migration: 1 inventory, 2 plan, 3 change, 4 check.

An example with a role, the material inside tags first, the question last and permission to say it does not know:

You are an experienced Windows server administrator.
<log>
2026-11-03T08:14:22 [ERROR] server01 spooler: Print job failed
2026-11-03T08:15:01 [WARN] server01 w32time: Time sync delayed
2026-11-03T08:15:40 [INFO] server01 spooler: Service restarted
</log>
Which of these lines is probably a fault and which is just a warning? If the log is not enough to answer, say so and tell me what information you need.

Same need, five prompts

The same need, cheap coffee, can be asked in five ways. The more precisely you say what you want, the more Claude can do, but at the same time it becomes clear what it needs around it: a search tool, information about your location, or a place where the task is run. Here are the first four. The fifth is in module 9.

1. A vague wish

I want cheap coffee
  • What Claude can do: guess what you mean. It can give general tips (comparing coffee packages, price per kilo, sale periods) or ask you back what you are after.
  • Tool and plan: an ordinary conversation, Free is enough. No search is needed, because nothing up to date is looked up.
  • What is missing: everything. Claude does not know whether you are looking for a shop, a buying tip or a cafe, or where you are.

2. A concrete search

Find the cheapest coffee deal near me
  • What Claude can do: search the web and gather the deals it finds. It tells you which sources the information comes from.
  • Tool and plan: web search in claude.ai. You turn it on from the chat's + button under Web search. According to the help article, Free users have usage limits and web search uses them. On Team and Enterprise accounts an administrator must first enable search. Help: support.claude.com.
  • What is missing: your location. Give a city or a postal code, because "near me" tells Claude nothing. Always check the price and validity on the shop's own page, because a search finds only what is on the web.

3. A recurring task

I want to regularly find out where to get the cheapest coffee, based on my postal code
  • What Claude can do: repeat the search on an agreed schedule. In Claude Cowork you schedule the task from Scheduled in the sidebar. According to the help article, a task can also do web research.
  • Tool and plan: Cowork and scheduled tasks. According to the help article, "Scheduled tasks are available on all paid plans (Pro, Max, Ultra, Team, and Enterprise)". The Free account does not have them. If a task needs local files or apps, it runs only locally. Help: support.claude.com.
  • What is missing: the postal code, the schedule (how often), and where the result goes and how the comparison is made. Provide these, and the task is ready to be scheduled.

4. Your own app

Build an app that fetches coffee deals from nearby stores
  • What Claude can do: write the code for the app and advise how to run it. Everything works only once it is known where the deal data comes from.
  • Tool and plan: Claude Code (modules 6 and 7), which requires at least a Pro plan. A lighter option is to ask for a small app in claude.ai (module 3).
  • What is missing: almost all the decisions: where the app runs, what language it is written in, where the deals are fetched from, where the history is stored, how the location is given and how the results are ordered. Without them Claude has to guess.

In prompt 5 these decisions have been made, and Claude has been told that it must ask for the rest: prompt 5 in module 9.

Exercises

1. Improve a weak prompt

Requires: a Claude account (Free is enough). No account? Write the prompt on paper and try it on a partner's machine.

First send the prompt "Make a regex that finds errors in a log". Then write a better version with context, example lines and the wanted format, and compare the answers.

Show example answer

A better prompt could be:

Write a .NET/PowerShell regex that picks out the time, level and message from lines
where the level is ERROR or FATAL.
Matches: "2026-11-03T08:14:22 [ERROR] spooler: Print job failed"
Does not match: "2026-11-03T08:15:40 [INFO] spooler: Service restarted"
Give the regex, a short explanation and a Select-String example.

The answer could be ^(\S+) \[(ERROR|FATAL)\] (.+)$ with the example Select-String -Path .\app.log -Pattern $rx. Always test a regex with your own lines.

2. A ticket reply from an example

Requires: a Claude account (Free is enough). No account? Work with a partner.

Give Claude one earlier, proven ticket reply as a style example (without personal data). Then ask for a reply in the same style to the ticket: "Outlook keeps asking for the password after a password change."

Show example answer

A good reply follows the tone and length of the example, states the likely cause (old credentials in the cache) and gives 2-4 numbered steps: close Outlook, remove the old credentials in Windows Credential Manager, start Outlook and sign in with the new password. At the end it says to get in touch if the problem continues.

3. Let Claude ask first

Requires: a Claude account (Free is enough). No account? Work with a partner so that one of you answers Claude's questions.

Ask Claude to make a runbook for a server's monthly update, but tell it to first ask for the information it needs, one question at a time. Answer the questions and finally ask for the runbook.

Show example answer

Claude asks, for example: which operating system, whether it is a cluster or a single server, the maintenance window, how the backup is verified, who approves the restart, and how to roll back if the update fails. The finished runbook is a numbered list with checks before, during and after, and a rollback plan.

4. Optional: climb the ladder with a vague IT request

Requires: a Claude account (Free is enough). No account? Write four versions on paper and compare with a partner.

Take a vague request: "The printer is not working." Write four steps from it in the style of the coffee example: a vague wish, a concrete request, a recurring task, and a finished assignment where you state the decisions and ask Claude to ask for the rest. At each step, think about what Claude needs and what it is missing.

Show example answer
  1. The printer is not working. Claude can only guess and ask: which printer, what happens.
  2. The office Canon printer does not print from a Windows 11 machine, the error message is "Printer is not available". What do I check first? Now there is a model, an operating system and an error.
  3. Once a week I want a summary of the printer faults that recur most often in tickets (without personal data). This needs a schedule, the ticket data and a place for the summary to go.
  4. Write a PowerShell script that checks the state of the print queue and restarts the print spooler when the queue is stuck. Do not change anything until I have approved the command. Ask me for the missing details until we agree. If you do not know something, say that you do not know.

At each step the prompt says more: what, where, how often and what Claude may change.

Optional: the most common beginner mistakes

  1. A prompt that is too short: "fix this" with no error, version or goal.
  2. Running without checking: a script straight into production without a test or a -WhatIf run.
  3. Pasting too much: a whole log or credentials, when an excerpt and placeholders would do.
  4. One endless conversation: all topics in the same thread, the limit runs out and the answers get mixed up.
  5. Correcting afterwards: five correcting messages instead of editing the original.
  6. Believing the confident tone: a confident answer is not proof. Check it.
  7. Not stating the format: a long essay when you needed a three-line command.
